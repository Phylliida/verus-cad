1. SS13 / BYOND DM

Philosophy

BYOND's DM (Dream Maker) language collapses three things that most engines keep separate: the type system, the prototype/template system, and the runtime instance API. Every entity in the world — items, mobs, tiles, regions — lives at a single address in a global tree of type paths. A path like /obj/item/weapon/sword is simultaneously a type, a prototype with default values, and a globally addressable identifier you can pass around as a first-class value.

The atom tree

Everything that exists in the world descends from /atom. The canonical hierarchy:

/datum                  // root for non-world objects (data containers, controllers)
/atom                   // anything that exists somewhere
  /atom/movable         // can move
    /obj                // inanimate world objects (items, machines, structures)
    /mob                // living things, players, NPCs
  /turf                 // floor/wall tiles (fixed grid cells)
  /area                 // regions (e.g. "bridge", "engineering")

Definitions are open paths

You don't declare classes. You declare paths, and re-declaring a path simply adds to the existing definition at that location. There is no class Foo extends Bar — the slash in the path is the inheritance.

/obj/item
    var/name = "item"
    var/weight = 1
    var/desc = "An object."

/obj/item/weapon
    var/damage = 5
    var/sharp = FALSE

/obj/item/weapon/sword
    name = "sword"
    damage = 20
    sharp = TRUE
    icon_state = "sword"

/obj/item/weapon/sword/legendary
    name = "Caladbolg"
    damage = 80

Each block adds variables (var/x) or overrides defaults (x = ...) at that path. legendary automatically inherits everything from sword, which inherits from weapon, which inherits from item.

Procs (methods)

Behavior is attached to paths via proc/:

/obj/item/weapon/sword/proc/swing(mob/target)
    target.take_damage(damage)
    visible_message("[src] swings at [target]!")

/obj/item/weapon/sword/legendary/swing(mob/target)
    ..()                          // call parent implementation
    target.set_on_fire()

Subpaths override procs by re-declaring them without the proc/ keyword. ..() calls the parent implementation. src is the receiver.

Engine-known variable names

Many vars (icon, icon_state, density, opacity, layer, pixel_x) are read directly by the BYOND engine for rendering and physics. Setting density = TRUE on an atom makes it block movement; the author writes nothing else. This is the closest DM gets to a declarative tag system: well-known variable names that the engine treats as commands.

Instantiation

Paths are first-class. new /obj/item/weapon/sword(loc) spawns an instance. typesof(/obj/item) returns every descendant path. You can store paths in variables, dispatch on them, generate them at runtime.

Maps

Map files (.dmm) are a separate text format that maps single-character keys to (/turf/path, /area/path, list-of-/obj-paths) tuples, then lays them out in a grid. The map format does not reuse DM syntax — it's a parallel mini-language that references the type tree.

The whole worldview: the universe of "things that can exist" is a single global tree. Definitions and instances differ only in whether new has been called. Code lives on the tree, not about the tree.

2. Dwarf Fortress raws

Philosophy

Dwarf Fortress's game logic is a fortress (sorry) of compiled C++. The raws are the entire moddable surface: plain-text files in data/vanilla/<module>/objects/ defining creatures, materials, plants, reactions, body plans, languages, items, buildings, interactions, and more. The engine reads them once during world generation and never again. Raws are pure data — there is no scripting, no expressions, no conditionals. Just declarations the engine knows how to interpret.

File structure

Every raw file follows the same shape:

creature_dwarf            ← bare line: file ID (must match filename)

[OBJECT:CREATURE]         ← what kind of object lives in this file

[CREATURE:DWARF]          ← first object: type:id
    [NAME:dwarf:dwarves:dwarven]
    [DESCRIPTION:A short, sturdy creature fond of drink and industry.]
    ...

[CREATURE:GOBLIN]         ← next object
    ...

Token syntax

Everything inside an object is a bracketed token: [TAG:arg1:arg2:...]. Whitespace and indentation are purely cosmetic — the parser only cares about brackets. Anything outside brackets is a comment.

[CREATURE:DWARF]
    [DESCRIPTION:A short, sturdy creature fond of drink and industry.]
    [NAME:dwarf:dwarves:dwarven]
    [CREATURE_TIER:3]
    [BIOME:MOUNTAIN]
    [BIOME:ANY_TEMPERATE_FOREST]
    [INTELLIGENT]
    [BENIGN]
    [BODY:HUMANOID_NECK:2EYES:2EARS:NOSE:2LUNGS:HEART:GUTS:ORGANS:HUMANOID_JOINTS:5FINGERS:5TOES:MOUTH:TEETH:RIBCAGE]
    [BODY_DETAIL_PLAN:STANDARD_MATERIALS]
    [BODY_DETAIL_PLAN:STANDARD_TISSUES]
    [USE_MATERIAL_TEMPLATE:SKIN:SKIN_TEMPLATE]
    [BODY_SIZE:0:0:3000]
    [BODY_SIZE:1:168:15000]
    [BODY_SIZE:12:0:60000]
    [CASTE:FEMALE]
        [FEMALE]
    [CASTE:MALE]
        [MALE]
    [SELECT_CASTE:ALL]
        [PHYS_ATT_RANGE:STRENGTH:450:950:1150:1250:1350:1550:2250]

Three composition mechanisms

(a) Templates

Pre-defined bundles of tags that get inlined where requested. The classic is USE_MATERIAL_TEMPLATE:LOCAL_NAME:TEMPLATE_ID, which copies a material definition into the current creature under a local name.

[USE_MATERIAL_TEMPLATE:SKIN:SKIN_TEMPLATE]
[USE_MATERIAL_TEMPLATE:BONE:BONE_TEMPLATE]
[USE_MATERIAL_TEMPLATE:BLOOD:BLOOD_TEMPLATE]

(b) Selectors (scope narrowing)

A selector token shifts the scope of all following tags to a sub-element. After [SELECT_CASTE:MALE], every subsequent tag applies only to the male caste until another selector appears.

[SELECT_CASTE:FEMALE]
    [BODY_SIZE:1:168:14000]
[SELECT_CASTE:MALE]
    [BODY_SIZE:1:168:15000]
    [BEARD_TAGS]
[SELECT_CASTE:ALL]
    [HOMEOTHERM:10067]      ← applies to both

(c) Variations

Reusable tag transforms applied with APPLY_CREATURE_VARIATION:NAME. Variation files declare patches: add tags, remove tags, convert tags. This is how a single STANDARD_BIPED variation can be sprinkled onto twenty creatures.

[CREATURE_VARIATION:STANDARD_BIPED]
    [CV_NEW_TAG:GAITS_BIPED_STANDARD]
    [CV_NEW_TAG:STANCE_CLIMBER]
    [CV_REMOVE_TAG:NO_GAIT]

[CREATURE:GOBLIN]
    [APPLY_CREATURE_VARIATION:STANDARD_BIPED]

There is also COPY_TAGS_FROM:OTHER_CREATURE, which inlines another creature's entire tag list, and GO_TO_END / GO_TO_TAG selectors for editing existing tag streams.

Cross-references

Tokens reference other objects by ID strings: [BIOME:MOUNTAIN], [BODY:HUMANOID], [REAGENT:flux:150:STONE:NO_SUBTYPE:INORGANIC:FLUX]. The engine resolves these against the global registry of all loaded objects after parsing. There is no namespacing; every ID is global within its object type.

The whole worldview: the world's content is a flat database of (TYPE, ID) records, each carrying a bag of tags the engine knows how to interpret. Composition happens by templating, scope-narrowing, and patching — not by inheritance.

3. Structural similarities

Despite radically different surface syntax (slash-paths vs bracket-tags) and runtime models (interpreted scripting vs static data load), the two systems converge on the same core abstractions. These are the parts you almost certainly want to steal.

3.1 Single global ID space, no imports

Both systems give every defined thing one canonical identifier in a flat namespace. /obj/item/weapon/sword and CREATURE:DWARF are equally unambiguous. There is no module system, no import statement, no fully-qualified-name dance. New definitions just show up by being parsed.

3.2 Definition is property-bag

Both ultimately describe a "kind of thing" as a bundle of named properties + a list of capabilities/tags. DM uses named vars (damage = 20); DF uses positional token args ([BODY_SIZE:1:168:15000]). But the shape is identical: this kind of thing has these features.

3.3 Engine-known vocabulary drives behavior

The author rarely writes behavior. They use the right name and the engine takes over. DM: density = TRUE blocks movement. DF: [FLIER] grants flight. Both are essentially declarative tag systems where the engine has a hardcoded interpretation of certain identifiers. The vocabulary is the API.

3.4 Definition extension over class hierarchy

Neither system asks you to plan a clean inheritance hierarchy upfront. Both let you "open" an existing definition and add to it:

  • DM: re-declare the same path; new vars and procs append.
  • DF: [SELECT_CREATURE:DWARF] followed by more tags edits an existing creature.

This is closer to open prototypes than classical OOP. Definitions accumulate.

3.5 Composition primitives

Both provide a way to share chunks of definition across multiple things without forcing them into a parent type:

SystemMechanismEffect
DMpath nesting (/obj/item/weapon)Children inherit parent vars/procs
DM"abstract" intermediate pathsShared base, never instantiated directly
DFUSE_MATERIAL_TEMPLATEInline a named template under a local alias
DFAPPLY_CREATURE_VARIATIONApply a reusable patch (add/remove/convert tags)
DFCOPY_TAGS_FROMInline another whole definition

3.6 Definition vs instance separation

In both systems the file you author is the definition, never the live game state. DM has new(); DF has world-gen. The text file is the prototype; instances are spawned elsewhere and carry mutable state independently.

3.7 Definitions reference other definitions by name

Cross-references are by string ID, not by import or pointer. BODY:HUMANOID refers to a body plan defined in some other file. /obj/item/weapon/sword can refer to /datum/material/iron. Late binding at load time. Missing references error at parse, not at use.

3.8 Authoring model: declarative + grouping

Authors mostly write what things are, occasionally write what things do. Most content is declarative; behavior either lives in the engine (DF) or in a thin proc layer (DM). The grouping mechanism (paths in DM, files+templates in DF) lets authors organize hundreds of definitions without ceremony.

4. Where they diverge

SS13 / DM

  • Turing-complete scripting embedded
  • Code and data unified in one tree
  • Inheritance via path structure
  • Runtime is interpreted; mods can change anything
  • Authors write actual game logic
  • Map format is separate but references the tree
  • One root tree

Dwarf Fortress raws

  • Pure data, no logic
  • Engine in C++; raws merely configure it
  • Composition via templates and variations
  • Loaded once at world-gen, then frozen
  • Authors only configure existing systems
  • No map analog — world is generated procedurally from raws
  • Many parallel object types (CREATURE, MATERIAL, REACTION, …)

The deep philosophical split: DM trusts the author with a programming language; DF trusts only a vocabulary. DM scales to arbitrary new behaviors at the cost of debugging hell; DF scales to thousands of well-formed creatures at the cost of being unable to add fundamentally new mechanics without a C++ patch.

5. Implications for an LLM-driven DSL

Given an LLM is going to be reading, writing, and possibly executing this DSL — or at least reasoning about its definitions — here are the design pressures the SS13/DF lineage suggests.

5.1 Favor the DF token style for LLM legibility

Bracket-token syntax is unambiguous to parse, easy to validate, and trivially diffable. Each tag stands alone — the LLM can add or remove one tag without disturbing the surrounding definition. DM's open-path syntax is concise for humans but harder to validate piecemeal: indentation matters, var/proc declarations are positional, and errors cascade.

A DF-flavored token line is a discrete fact. An LLM can generate one tag at a time and the file remains well-formed.

5.2 Steal the path-as-identifier idea

Even within a DF-style format, hierarchical IDs (creature/dwarf/legendary or item.weapon.sword) give the LLM an organizational handle that flat IDs lack. Path prefixes implicitly cluster related things, which helps an LLM retrieve and extend the right family of definitions.

5.3 Engine-known vocabulary as the contract

The most important design decision is the tag vocabulary. This is what the LLM must learn. Treat tags like a controlled language:

  • Stable, documented set of tags with clear semantics
  • Each tag = one well-defined engine effect
  • Easy to enumerate ("here are all valid tags") for prompting
  • Validation rejects unknown tags loudly — helps the LLM correct itself

5.4 Composition over deep inheritance

DM's deep paths (5–6 levels) are hard for an LLM to reason about because the effective definition is the union of many ancestors. DF's templates+variations are easier: each unit is locally complete, and composition is explicit (APPLY_X) rather than implicit (path nesting). Lean toward shallow types + named patches.

5.5 Strict declarative core, optional behavior layer

Keep the LLM's primary surface declarative — definitions and tags only. If you need novel behaviors, expose a second layer (a proc-like attachment, or LLM-generated-at-runtime behavior dispatch) that's clearly separate from the definitions. Mixing them à la DM tempts the LLM into writing buggy logic where a tag would do.

5.6 Open definitions for incremental authorship

Both systems let you add to an existing definition without rewriting it. This is gold for an LLM working iteratively: it can emit a small [SELECT_CREATURE:DWARF] [NEW_TAG] patch instead of regenerating the whole creature. Make sure your DSL has a SELECT-style mechanism.

5.7 Cross-reference by string ID with parse-time resolution

Globally unique IDs and late-bound references mean the LLM doesn't have to track imports or scopes. It just names the thing. Validate references at load time and produce specific errors ("no creature DWARG, did you mean DWARF") that the LLM can act on.

5.8 A possible minimal shape

Synthesizing the above, a starter DSL might look like:

# file: creatures/dwarf.def

[creature/dwarf]
    [name: dwarf, dwarves, dwarven]
    [biome: mountain]
    [biome: temperate_forest]
    [body: humanoid_neck, 2_eyes, 2_lungs, heart, ribcage]
    [trait: intelligent]
    [trait: industrious]
    [drinks: alcohol]
    [size: adult, 60_kg]

[creature/dwarf/legendary_smith]
    [extends: creature/dwarf]
    [trait: master_artisan]
    [skill: smithing, legendary]
    [llm_persona: "A weathered dwarf who has forged
                   the great gates of three mountainholds."]

Notes on this shape:

  • DF-style brackets, DM-style path IDs.
  • extends: as an explicit composition tag rather than implicit path inheritance.
  • Comma-separated args inside tags for readability (parse-equivalent to DF colons).
  • An llm_persona tag (or similar) carries free-text payload the LLM can use to drive behavior at runtime — bridging the declarative core to an LLM behavior layer without baking logic into the file.

5.9 Things to nail down early

  1. Tag vocabulary versioning. The LLM will memorize tags; renaming is costly. Pick names you'll keep.
  2. Validation feedback format. Errors should name the specific token and offer suggestions — this is the LLM's debugging signal.
  3. Where behavior comes from. Engine-fixed? LLM-at-runtime? A small embedded scripting layer? Decide before you let DM-style temptations creep in.
  4. How instances differ from definitions. DF freezes raws at world-gen; DM keeps types live. For an LLM-driven world, you probably want live definitions (the LLM might invent a new creature mid-game).
  5. How the LLM discovers what exists. Both DM and DF assume the author has read the source. Your LLM needs an enumeration interface — something like list creatures, describe tag X.
