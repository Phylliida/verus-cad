# BUG: under `--lean-backend`, the aggregate `main.lean` drops the source `import` lines

**Severity:** breaks every tutorial chapter whose proofs use a Mathlib tactic
(`nlinarith`, `linarith`, `ring`, …) under `--lean-backend` — i.e. sum_to_n,
factorial, pow_by_squaring, fib_iter, fibonacci, strong_induction. gcd is the
only one unaffected (it uses core tactics only).

**Status:** ✅ RESOLVED 2026-06-06 (tactus `f949022`). Found while migrating
chapters to `--lean-backend`.

## Resolution

Root cause (confirmed): the source `import Mathlib.Tactic.X` lines are attached
**per-fn** at macro-expansion (`builtin_macros/src/syntax.rs:4831`), gated on
`tactic_by || tactus_auto`. Under `--lean-backend` a plain exec fn (`fn main`)
routes to Lean *without* either attr, so its `lean_imports` is empty — yet its
generated file's preamble over-approximates and emits every proof fn (e.g.
`sum_formula`'s `nlinarith`). Hence `main.lean` dropped the Mathlib import and
`nlinarith` was "unknown tactic". (The bug's "likely location" was close but
named the wrong mechanism — `insert_nat_coercions` is unrelated and was deleted
in the Part 2 gate; the import threading is what mattered.)

Fix: `krate_preamble` now emits the union of imports over the fns **actually
emitted into this file** — `root_fns` + `helpers_to_emit` — rather than just the
current fn's. Scoped to file content, so it's neither over-broad (no blanket
cross-source-file import leak — a proof-fn file gets only its root + downward-
closure helpers) nor under-broad (a cross-file proof fn pulled into an exec
file's over-approximated preamble still gets its imports). `helpers_to_emit` is
hoisted above the import block (Lean requires imports first).

Observationally a no-op today (every Lean verus invocation is single-file, so
file-scope == krate-scope), but correct for the multi-file `lean-backend` crates
REFACTORING.md anticipates.

Pinned by `test_plain_exec_fn_file_gets_file_level_import`. `sum_to_n.rs
--lean-backend` returns to **6/0**, `main.lean` carries `import
Mathlib.Tactic.Linarith`. Full suite **489/0**, lean_verify **269/0**, vstd
**1530/0**. (factorial / pow / fib_iter / fibonacci / strong_induction should
likewise return to 0 errors under `--lean-backend`, modulo any chapter-specific
glue.)

**This is fully verified — not a guess.** Prepending the missing import to the
generated file makes it compile clean (see "Proof" below).

## Symptom

`verus --lean-backend chapters/01-sum-to-n/sum_to_n.rs` → `5 verified, 2 errors`,
both errors `unknown tactic` / `unsolved goals`, attributed to `main`:

```
error: Lean tactus_auto failed for main:
       unknown tactic
error: Lean tactus_auto failed for main:
       unsolved goals:
         case succ
         k : Nat
         ih : 2 * sum_to k = k * (k + 1)
         ⊢ 2 * (k + 1 + sum_to k) = (k + 1) * (k + 1 + 1)
```

The goal is closed by `nlinarith [ih]` — but `nlinarith` is reported as an
**unknown tactic**, because Mathlib isn't imported in the file being checked.

## Root cause

Under `--lean-backend`, the file Tactus actually checks is the **aggregate**
`target/tactus-lean/<file>/main.lean`, which bundles *all* of the source file's
theorems (`sum_zero`, `sum_three`, `sum_formula`, `_tactus_ensures_main_1`, …).
Its header is:

```lean
-- Auto-generated by Tactus. Do not edit.
import Lean          -- ← NO `import Mathlib.Tactic.Linarith`
set_option ...
```

But the **per-fn** files generated alongside it (`sum_formula.lean`,
`fact_monotone.lean`, …) *do* carry the source import:

```lean
import Mathlib.Tactic.Linarith     -- first line of sum_formula.lean
```

So the source's `import Mathlib.Tactic.Linarith` (declared inside `verus! { }`)
is threaded into the per-fn files but **dropped from the aggregate `main.lean`**.
Any `nlinarith`/`linarith`/`ring` in that aggregate is then `unknown tactic`.

## Proof (each step run)

| Check | Result |
|---|---|
| `lake env lean` on generated `sum_formula.lean` (has the import) | **exit 0**, clean |
| `lake env lean` on generated `main.lean` (no import) | `unknown tactic` at `nlinarith` (l.466), `unsolved goals` (l.457) |
| same `main.lean` with `import Mathlib.Tactic.Linarith` **prepended** | **exit 0**, clean |

The last row is the proof: the missing import is the *entire* problem. The
chapter proofs are correct; nothing in the `.rs` needs changing.

`factorial/main.lean` is the same shape — header `-- Auto-generated …` with no
Mathlib import, and it contains `nlinarith`/`linarith` calls — so factorial,
pow, fib_iter, fibonacci, strong_induction all fail identically.

## Likely location

`source/lean_verify/src/generate.rs` threads `imports: &[String]` into the
per-fn emission paths (`emit_proof_fn` / `emit_exec_fn` / `krate_preamble`,
which does `for imp in imports { out.push_str("import …") }` ~line 232). The
**aggregate / `main.lean`** generation path is evidently not being handed (or
not emitting) that same `imports` list. Thread the source imports into the
aggregate file the same way the per-fn files get them.

## Repro / regression guard

- Minimal: any `--lean-backend` file with a proof that uses `nlinarith`:
  ```rust
  spec fn s(n: nat) -> nat decreases n { if n == 0 { 0 } else { n + s((n-1) as nat) } }
  proof fn t(n: nat) ensures 2 * s(n) == n * (n + 1) by {
      induction n with
      | zero => unfold s; decide
      | succ k ih => unfold s; rw [if_neg (by omega : (k+1:Nat) ≠ 0)];
                     rw [show ((↑(k+1):Int)-1).toNat = k from by omega]; nlinarith [ih]
  }
  ```
  → `unknown tactic` (aggregate main.lean lacks the import).
- Guard: assert the generated `main.lean` begins with the same `import` block as
  the per-fn files.

## After the fix

All migrated chapters should return to `0 errors` with no `.rs` changes — their
proofs already compile when the import is present (verified via `lake env lean`).
gcd already passes (`3 verified, 0 errors`).
